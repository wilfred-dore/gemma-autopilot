Rapport de projet

Gemma²

Un agent autonome qui optimise et explique son propre déploiement d'inférence LLM.

Hackathon Paris Gemma 4 · 42 Paris Langage : Python ≥ 3.10 Licence : Apache-2.0 Modèle cible : Gemma 4 27B-A4B-it

1. Résumé exécutif

En une phrase Gemma² est un agent IA construit sur Gemma 4 qui se benchmark lui-même en boucle fermée, diagnostique les goulots d'étranglement en langage naturel, modifie sa propre configuration de déploiement (vLLM), puis se rebenchmarke: jusqu'à ce que les gains deviennent négligeables.

Le projet répond à une question concrète : peut-on confier à un LLM la responsabilité d'optimiser le serveur qui le fait tourner ? La réponse démontrée ici est oui, avec deux contraintes fortes :

  • Contrainte de latence: TTFT (Time To First Token) ≤ 500 ms. Toute configuration qui la viole est éliminée du classement.
  • Axe d'efficacité énergétique: joules/token tracés à chaque run, car l'énergie compte autant que la vitesse.

Chaque configuration produite par l'agent est mesurée sur un vrai GPU (H100 PCIe) et publiée en temps réel dans un dashboard HTML. Un baseline human expert sert de référence compétitive.

2. Contexte et motivation

Pourquoi l'auto-optimisation ?

Déployer un LLM en production implique de nombreux hyperparamètres interdépendants : taille des batchs (max_num_seqs), prefix caching, power cap GPU, concurrence client… L'espace de recherche est trop large pour une exploration manuelle, et les interactions entre paramètres sont non-linéaires. Un agent capable de raisonner sur des métriques réelles et d'itérer plus vite qu'un humain est donc une piste naturelle.

Pourquoi Gemma 4 ?

Gemma 4 supporte nativement le function calling via le parser --tool-call-parser gemma4 de vLLM. L'agent utilise cela directement : chaque action (lancer un benchmark, ajuster le power cap, faire une recherche) est exprimée comme un appel d'outil structuré, sans couche d'abstraction supplémentaire.

Charge de travail cible

Le benchmark simule la génération de documents confidentiels (brevets pre-dépôt, rapports médicaux, articles d'investigation anonymisés): une classe de workloads qui justifie l'inférence locale : contexte d'entrée long (300–800 tokens), sortie structurée longue, fort stress sur le KV cache et le batching.

La boucle d'optimisation

Diagnostic en langage naturel L'agent reçoit les métriques du run précédent (tokens/s, TTFT, ITL, joules/token) et explique en 2–3 phrases son interprétation : memory-bound ? latency-bound ? queue saturation ? energy tradeoff ?
Choix d'action (un seul outil à la fois) L'agent appelle un outil : modifier la concurrence, activer/désactiver le prefix caching, ajuster le power cap, ou faire une recherche externe si le résultat est surprenant.
Exécution et mesure bench_runner.py lance vllm bench serve, parse sa sortie (tokens/s, TTFT, ITL), mesure l'énergie en temps réel via NVML (delta du compteur cumulatif, précision Volta+), et retourne un RunResult JSON complet.
Journal & leaderboard Chaque run est ajouté au journal JSONL et au state.json. Le leaderboard attribue un score = tokens/s si TTFT ≤ 500 ms, sinon 0. Le dashboard se rafraîchit automatiquement.
Arrêt adaptatif Quand les gains estimés descendent sous ~3 %, l'agent appelle report_done avec un résumé en langage naturel de la stratégie et des résultats.

5. Composants clés

Agent (agent.py)

Le système repose sur un system prompt fortement contraignant qui impose à Gemma 4 :

  • Un seul appel d'outil par tour (évite les séquences ingérables)
  • Un raisonnement explicite avant chaque action (traçabilité)
  • De commencer par l'extrémité agressive de la plage de config, puis d'adapter
  • D'appeler search_web ou search_papers face à un résultat surprenant

Un fallback JSON est intégré : si vLLM ne retourne pas de tool_calls parsés (edge case), l'agent relance avec une demande de JSON brut. Même chemin de dispatch: la démo ne peut pas mourir sur un bug de parseur.

Guardrails (tools.py)

Tous les arguments sont vérifiés à l'entrée. Un rejet retourne un JSON explicatif que le modèle peut lire et corriger :

🔒
max_num_seqs : 1–512 · concurrency : 1–64 · power_cap_w : 200–350 W (plage H100 PCIe vérifiée sur le matériel)
🔒
Liste blanche d'outils : toute tentative d'appeler un outil inexistant retourne {"error": "unknown tool"}

La classe Ctx (contexte d'exécution) est entièrement injectable via Ctx.for_tests() : les tests unitaires n'ont pas besoin de GPU ni de serveur vLLM.

Mesure d'énergie (power.py)

EnergyMeter utilise nvmlDeviceGetTotalEnergyConsumption: le compteur cumulatif en millijoules disponible sur Volta+. Un delta d'entrée/sortie de contexte (with EnergyMeter() as m:) est plus précis qu'un sondage périodique. Résultat : joules totaux + watts moyens pour le run.

Dataset (datasets/)

30 prompts générés synthétiquement, répartis en trois classes de documents confidentiels :

  • Brevets pre-dépôt: 2 scénarios de base × 5 variations de paramètres
  • Rapports médicaux sous privilège: idem
  • Articles d'investigation anonymisés: idem

300–800 tokens d'entrée, longue sortie structurée attendue. Ce profil stress le KV cache et le batching bien mieux que des tokens aléatoires: exactement ce que l'agent doit apprendre à optimiser.

Dashboard (dashboard.html)

Page HTML standalone qui poll runs/state.json à intervalle régulier. Affiche :

  • Tuiles de résumé (meilleur throughput, meilleure énergie, nombre d'itérations, leader)
  • Graphes SVG : tokens/s et joules/token par run (points violacés = violation TTFT)
  • Leaderboard trié par score (0 si contrainte TTFT violée)
  • Trace de raisonnement de l'agent (chaque décision annotée)

Mode replay disponible via ?replay dans l'URL pour rejouer une session passée.

8. Démarrage rapide

Prérequis

Python ≥ 3.10 vLLM NVIDIA GPU (Volta+) SERPAPI_API_KEY (optionnel)

Installation

pip install -e .
# ou
pip install pynvml codecarbon requests

Lancement du serveur vLLM

vllm serve google/gemma-4-27b-it \
  --tool-call-parser gemma4 \
  --port 8000

python -m autopilot.agent --iters 8 --base-url http://localhost:8000

Dashboard

Ouvrir dashboard.html dans un navigateur. Il poll runs/state.json automatiquement.

Tests

pytest tests/   # aucun GPU requis (Ctx.for_tests() injecte des stubs)

9. Points techniques notables

Design by contract, pas by prompt Les guardrails sont du code Python pur: pas des instructions dans le prompt. Un argument hors plage retourne un JSON d'erreur que le modèle lit et corrige. Le système ne peut pas sortir de la plage sûre même si le modèle hallucine.
Mesure d'énergie précise sans sampling NVML GetTotalEnergyConsumption est un compteur hardware cumulatif. Le delta entrée/sortie du contexte Python donne l'énergie réelle du run, sans erreur d'intégration trapézoïdale.
Fallback JSON robuste Si le parser de tool calls vLLM échoue sur un edge case, l'agent relance avec un prompt forçant du JSON brut. Même chemin de dispatch: la démo reste opérationnelle quoi qu'il arrive.
Injectabilité totale pour les tests Ctx.for_tests() remplace toutes les fonctions I/O (benchmark, power, HTTP) par des stubs. Tests unitaires complets sans GPU ni réseau.
Limites actuelles Le projet ne modifie pas (encore) la quantification ou les paramètres de mémoire KV (--gpu-memory-utilization). La plage du power cap est figée pour H100 PCIe. Le dataset de benchmark est synthétique.
